### 1.4 这三项"零违反"说明什么

1. **下限是程序造成的硬边界，不是硬件抖动**：8 组、88 人、31,334 个 RT 精确落在 `T + 200ms + 2~3ms`；硬件故障只会随机丢失/抖动，不会产生跨被试整齐的边界。
2. **刺激期与掩蔽期是"死区"**：0 个试次落在 `[T, T+200ms)` → 这段时间按下的键**从未**被记录。
3. **反应窗口内采集完好**：0 个试次超过 deadline+60ms → 键盘在采集期内工作正常，不存在间歇失灵。
4. 显示器刷新率只影响画面时刻（量级 ≤1 帧 ≈ 16.7ms），**不影响按键能否被读取**。

### 1.5 为什么你会觉得"并不完全是这样"

| 原因 | 说明 |
|---|---|
| ① 下限不是 T，而是 T+200ms | 掩蔽/空白段占掉 200ms，且该段不采集按键；T=500ms 时下限是 **700ms**，用"T"核对就会觉得对不上 |
| ② **历史数据的组号与条件错位** | `raw` 里"组7/组8"文件内部参数是 **P120/T30/W800** 与 **P120/T80/W800**（＝现行代码条件表第 8、9 行）。若按现行条件表第 7 行（P0/T100/W1100）计算，会凭空得出 368 个"落在窗口内"、351 个"低于下限"的假异常——我第一遍统计正是踩了这个坑，改用**文件内 T/W** 后异常归零 |
| ③ 组号含义在历史上变动过 | 同一批数据在 `raw` 与 `emp_data` 里组号含义不同（`emp_data` 甚至没有 group7）。分析务必以**文件内 `P/T/W`**（v2 还会写入 `Mask`）为准 |

## 3. 问题①核查：RT 是否从刺激呈现时刻起算？符合科研惯例吗？

### 3.1 现有程序：是

- 代码：`responseTime = GetSecs() - stimulusFlipTime;`（v1 第 488/755 行；v2 在 `runOneTrial` 中同式），`stimulusFlipTime` = 刺激首次呈现的那一帧。
- 数据佐证：各组最小 RT 均等于 `T + 200ms + 2~3ms`；若 RT 从掩蔽结束起算，最小 RT 应接近 0，与实测不符 → **RT 确实从刺激 onset 起算**。

### 3.2 科研惯例：两种做法都常见，"全程记录"更稳

| 做法 | 说明 | 采用情况 |
|---|---|---|
| A. 掩蔽后才接收反应（v1 现状） | 掩蔽结束前的按键不被接收，RT 从刺激 onset 起算 | 后向掩蔽/掩蔽启动范式常见，可防止"掩蔽出现前就完成判断"污染掩蔽操纵 |
| B. 全程记录 + 事后分层（v2 采用） | 从刺激 onset 起记录所有按键，把"掩蔽前按下"标记为抢按，分析时按需剔除/单列 | 信息不丢失，可报告抢按率与被试策略 |

**裁定**：v1 在"RT 起算点"上正确；在"采集完备性"上不如做法 B。范式没有错，但**丢掉刺激期按键信息**是可改进项。

### 3.3 v1 的三处工程缺陷（不影响设计逻辑，但影响数据质量）

| # | 缺陷 | 后果 | v2 处理 |
|---|---|---|---|
| 1 | 掩蔽图逐试次 `imread` + `MakeTexture` | 每试次 10–20ms 开销，把 RT 推过 deadline（数据中 228/72/31… 个超限试次即来源） | 实验前预加载 10 张掩蔽纹理 |
| 2 | "过快（RT<150ms）"反馈分支不可达 | 死代码（RT 下限 ≥ 230ms） | 删除，改为"抢按（掩蔽前）"提示 |
| 3 | 未 `KbName('UnifyKeyNames')`；无输入校验；数据不含 link/matchkey/mask | 编号填错无法追溯（§4.3 的实例） | 增加 `UnifyKeyNames`、输入校验、CSV 追加 `Mask/Link/MatchKey/...`、会话日志 |

## 6. 新版程序：`Exp_Design_Formal_v2.m`

位置：`1_Code/Experiment/exp_matlab/Exp_Design_Formal_v2.m`（已通过 `checkcode`；并用桩函数对核心函数 `collectResponse` 做了 7 个用例的单元测试，全部 PASS）

**实现方式**：v2 以 **`Exp_Design_Formal.m`（v1，可正常运行）为基准逐行复制**，只改"按键采集"一处，
其余（启动顺序、开窗、学习阶段、指导语、试次数、平衡规则、时序）与 v1 完全一致 —— 因此 **v1 能跑，v2 就能跑**。

### 6.1 改动清单（最小改动）

| # | 改动 | 说明 |
|---|---|---|
| 1 | **按键采集改为 KbQueue 事件队列** | 每个试次在**刺激 onset 那一刻** `KbQueueFlush` 开始记录（丢弃注视期按键）；刺激呈现期、掩蔽期按下的键都会被带时间戳捕获 |
| 2 | **RT 口径不变** | RT 仍 = 按键时刻 − 刺激 onset；且改用按键事件的真实时间戳（不受轮询间隔影响，比 v1 略更准） |
| 3 | **抢按可配置** | 顶部 `REJECT_PREMASK = 0`（默认：抢按也计入并用 `Premask` 标记）/ `1`（抢按不计入，继续等掩蔽后的按键） |
| 4 | **新增 6 列**（追加在原 16 列之后） | `Mask, Link, MatchKey, Premask, NKeyBeforeMask, NKeyTotal` |
| 5 | **文件名加 `_v2` 后缀** | `EXP_data_group{G}_{S}_v2.csv` / `exp_group{G}_subject{S}_v2.txt`，与 v1 数据区分 |
| 6 | 开窗加一层保护 | 若 `OpenWindow` 因 PTB 同步测试失败报错，打印真实原因并自动以 `SkipSyncTests=1` 重试一次（v1 相同设置下若同步测试通过，则行为与 v1 完全一致） |
| 7 | 结尾打印会话小结 | 显示"有反应 / 抢按"次数，便于主试当场确认刺激期按键确实被记录 |

> 与 v1 相同的部分（未改）：逐试次 `imread` 加载掩蔽图（保持与旧数据一致的时序）、反馈逻辑（含 `<150ms 过快` 分支）、
> 学习阶段 60s、练习 P 试次、正式 10 blocks × 52 试次、编号↔联结/按键平衡规则。
